# Capabilities

Capability-based access grants for Cartopian-governed projects. Roles are user-named bundles of grants declared in `[roles.<name>]` tables in `cartopian.toml` (`grants = [...]`); enforcement keys on grants only — never on role names or prose role descriptions. **The vocabulary is closed and append-only**: names may be added in later protocol versions but are never renamed or removed, and unknown names are never silently accepted.

Review assignment is a separate concern. `[reviews].planning_role` and `[reviews].task_role` may point to any defined role name. The conventional `reviewer` label, a review-oriented description, and the `reviewer-like` preset do not by themselves assign that role to a review checkpoint. Conversely, assigning a role in `[reviews]` does not grant access. When containment is active, the operator must grant that role the capabilities its handoff needs.

## Vocabulary

Read grants (deliberately coarse; may be split finer later, append-only):

- `read:governance` — read management/strategy artifacts plus specs.
- `read:reports` — read reports and reviews.
- `read:prompts` — read the `prompts/` directory (the assignee's handoff).
- `read:work-roots` — read the product tree.

Write/act grants:

- `write:plan` — author plan artifacts.
- `write:lifecycle` — perform lifecycle mutations (task status, state, protocol files).
- `write:decisions` — record decisions.
- `write:reports` — write reports and reviews.
- `write:worktree` — mutate the product tree.
- `dispatch` — dispatch handoffs.

## Activation

- **Activation rule:** the first role in the resolved config that declares a `grants` key activates containment project-wide, all-or-nothing — there is no per-role mix of gated and ungated.
- **Ungated mode:** no role in the resolved config declares grants — gating is inactive and every session behaves as if all read and write grants were held (configs that predate the vocabulary work unchanged).
- **Activated mode:** resolution fails closed — a role with an unknown capability name, an explicitly empty grant list, or no declared grant set holds no grants (a typo never widens access); a session holding several roles gets the union of their grants.

## Presets

Preset names are valid anywhere a capability name is and expand to their grants at resolution time; the operator composes them per role (e.g. `grants = ["reviewer-like", "write:plan"]`). Preset names describe access shapes only; they do not select lifecycle policy or review assignment.

| Preset | Grants |
| --- | --- |
| `coder-like` | `read:prompts`, `read:work-roots`, `write:worktree`, `write:reports` |
| `reviewer-like` | `read:governance`, `read:reports`, `read:prompts`, `read:work-roots`, `write:reports` |
| `planner-like` | `read:governance`, `read:reports`, `read:prompts`, `write:plan` |
| `pm-with-planner` | `read:governance`, `read:reports`, `read:prompts`, `write:lifecycle`, `dispatch` |
| `pm-solo` | `read:governance`, `read:reports`, `read:prompts`, `write:plan`, `write:lifecycle`, `dispatch` |

`reviewer-like` includes the two direct-evidence reads used by both review workflows: `read:governance` covers governed task evidence and planning artifacts, while `read:reports` covers the preserved task-completion report and prior review output. It still grants no plan, lifecycle, decision, configuration, prompt, or worktree mutation authority. `coder-like` deliberately carries neither evidence-read grant because the PM curates an implementation assignment into its prompt. The PM presets stay out of `read:work-roots` and `write:worktree`.

## Enforcement

Structured-tool boundaries are enforced at the harness's native interception point — the Claude Code PreToolUse refusal adapter (`cli/claude_hook.py`) — keyed on the session's resolved grants only, never on role names or descriptions. For a mediated Claude handoff, `cartopian dispatch` exports the session role, bound project root, current Python interpreter, and exact resolved Claude executable; the Claude wrapper resolves the project's activation state and adds the refusal adapter through process-scoped `--settings` only when grants are active. Hook-enabled launches require those absolute executable bindings and validate containment before invoking Claude, so a work-root `PATH` entry cannot replace either executable between preflight and launch. Before starting its isolated (`-I -S`) output supervisor, dispatch strips inherited Bash/function/tracing, Bun/Node, loader, Python, and OpenSSL startup controls that could execute code before containment; the POSIX wrapper also starts Bash in privileged startup mode. The generated hook command captures the role, project root, canonical Cartopian config home, loaded legacy-global settings path, and every work root's canonical path plus launch-time device/inode as direct arguments. The hook revalidates those identities on each call and resolves the authored target before collapsing `..`, so a renamed root or symlink traversal cannot change its authority boundary. No project registration is required. In an activated dispatch, the hook denies structured reads and writes outside that bound project and its launch-captured work roots. Because a path-only PreToolUse decision cannot atomically bind Claude's later macOS file open, activated structured mutation tools do not write external work roots at all: with `write:worktree`, those mutations use Bash under the OS sandbox, which enforces the boundary at the filesystem operation. Structured reads still use the captured work-root grant decision. The binding makes that classification independent of registry order: another project's duplicate mapping can neither grant nor revoke this session's access, while an unbound legacy invocation fails closed when equally specific claims are ambiguous.

On native macOS and Linux, the same process-scoped settings enable Claude's OS sandbox for shell commands and child processes. The active and every registered Cartopian project directory, the active checkout's `.git` marker and resolved Git directory/common directory (including external linked-worktree metadata), and active Cartopian install/config/runtime roots are shell-read-only under that policy; declared work roots are shell-writable only when the dispatched role holds `write:worktree`. Before launch, Cartopian rejects symlink or hard-link aliases in the activated project/config/registry boundary and scans every effective shell-writable root—the authorized work roots plus Claude/Sandbox Runtime's existing fixed and per-UID temp, npm-log, and debug directories. Protected paths and writable roots must be disjoint in both directions; nested writable roots and protected paths overlapping implicit write exceptions refuse before launch so an ancestor rename cannot move a protected inode around a path-based deny. A multiply linked regular file is accepted only when every one of its names is inside that complete Cartopian-authorized writable-root set; a pre-existing cross-boundary hard link refuses launch, and protected regular files with multiple names are refused outright. Fresh cross-boundary links remain blocked by the attested deny-default sandbox. `CLAUDE_CODE_TMPDIR` and `CLAUDE_TMPDIR` are refused, while dispatch replaces inherited `TMPDIR`/`TMP`/`TEMP` with a direct, user-owned mode-0700 `~/.cartopian/claude-host-tmp` before Claude's version probe and real launch. That protected path holds the unsandboxed host SRT mux socket; attested Claude 2.1.278 separately sets sandboxed Bash `$TMPDIR` to its own writable per-user temp. On Linux, mountinfo coordinate validation additionally rejects nested mounts and bind-mount aliases whose underlying filesystem coordinates overlap a protected boundary. Sandbox startup is fail-closed, the unsandboxed retry escape hatch and Apple Events are disabled, and Cartopian adds no excluded-command or violation exception. Because Claude interprets sandbox paths containing `*`, `?`, `[` or `]` as glob syntax (or skips them), and line-oriented Git discovery cannot safely bind control-character paths, any policy path containing those characters refuses launch rather than weakening a literal boundary. Every accepted activated launch passes an empty `--setting-sources` value, excluding normal user, project, and local settings and therefore their hooks, plugins, environment values, and sandbox additions; cwd changes cannot hot-load a new exception from an authorized work root. Claude still loads the top-level `env` from its legacy global `.claude.json`, so Cartopian reads that file with Claude's one-BOM rule, fails closed on malformed UTF-8, rejects environment values that relocate `HOME` or temp controls, validates the remaining effective environment, and protects the file with the shell policy. Auto-memory is disabled for the activated process. Host-side helper execution is frozen too: explicit external-ripgrep mode is refused on POSIX; unsafe effective `PATH` or ripgrep overrides from the inherited environment or legacy global config are refused or protected; all pre-containment Git/version probes receive an explicit sanitized environment; and Cartopian protects the selected `rg` search chain on macOS plus the `rg`/`bwrap`/`socat` chains on Linux, refusing a writable-work-root intersection. The activated Stop hook binds its counter to a direct, user-private `stop-state` directory below the canonical protected Cartopian config root rather than inherited temp; counter reads/writes do not follow planted symlinks. Git metadata inside an authorized external product work root remains writable as part of that work root. Activated launches require Claude Code 2.1.278 or newer, the first build attested for this exact deny-default policy. WSL2 activated dispatches fail preflight pending attestation of Claude's optional interop-blocking seccomp layer. Activated native-Windows dispatches likewise fail preflight until Cartopian can attest both a shell sandbox and an exact native Claude executable chain. Completion-only hooks may run on native Windows, but a hook-bound launch requires a direct native Claude executable; an underlying `.cmd` or `.bat` shim is refused because it cannot preserve the exact settings argv boundary. Administrator-managed sandbox or hook-disabling settings remain explicit policy overrides outside Cartopian's control. Command text is never parsed as a security boundary. Shell reads remain a disclosed residual on accepted native macOS/Linux launches.

All activated Claude launches force `--strict-mcp-config` with no explicit MCP config. User/project/plugin MCP tools run outside the shell sandbox and have event names beyond the built-in-tool matcher, so they are excluded rather than treated as capability-scoped. The wrapper also disallows delegated-agent/worktree tools, team lifecycle tools, durable cron tools, peer-session message/file routing, and remote agent triggers (`Agent`/legacy `Task`, `EnterWorktree`, `ExitWorktree`, `TeamCreate`, `TeamDelete`, `CronCreate`, `CronDelete`, `CronList`, `SendMessage`, `SendFile`, and `RemoteTrigger`); the refusal hook independently denies any such call that still reaches PreToolUse. These tools can move or defer execution, route mutations through another session, or mutate shared Git metadata outside the captured project/work-root boundary. Normal user/project/local hooks and plugins are absent under settings isolation. Administrator-managed extensions remain operator-controlled trusted policy outside Cartopian's control.

**Write boundary** (the mutation tools `Write`/`Edit`/`MultiEdit`/`NotebookEdit`): governed project path-classes require the matching `write:*` grant. In an activated bound session, external work-root mutations are deliberately refused through these path-only tools and use sandboxed Bash instead; `write:worktree` controls whether that shell boundary is writable.

**Read boundary** (the read tools `Read`/`NotebookRead` and the search tools `Glob`/`Grep`; a pathless search gates on the session cwd it would sweep):

`Glob` and `Grep` authorize the whole directory surface they can sweep, not just the class of the directory path itself. A project-root search therefore requires `read:governance`, `read:prompts`, and `read:reports`, plus `read:work-roots` when a declared work root is nested below that search root; a narrower search requires only the reachable class or classes. An absolute `Glob` follows Claude's first-`*`/`?`/`[`/`{` search-base rule and overrides its separate `path`; parent traversal in the pattern suffix widens the authorization root conservatively. A broad search that can reach a nested foreign registered project is refused just as an exact read of that project would be.

| Path-class | Paths | Required grant |
| --- | --- | --- |
| governance | `specs/`, `phases/`, `tasks/`, `decisions/`, `STATE.md`, `BACKLOG.md`, `IMPLEMENTATION_PLAN.md`, `REQUIREMENTS.md`, `ROADMAP.md`, `STANDARDS.md`, `cartopian.toml`, `cartopian.local.toml`, and any unclassified project file | `read:governance` |
| reports | `reports/`, `reviews/` | `read:reports` |
| prompts | `prompts/` | `read:prompts` |
| work root | each declared work root | `read:work-roots` |

With the default assignee grants (`coder-like`), a dispatched session can read its own handoff prompt and the product work tree, and is refused reads of governance artifacts, specs, reports, and reviews.

With `reviewer-like`, a dispatched review session can read its handoff, the product tree, governed review evidence, and reports, and can write reports. The resolved bundle is independent of the role's operator-chosen name and of whether the handoff is manual or automatically launched; point-of-use enforcement still depends on the host boundary described above.

**Honest tiering.** `cartopian containment-matrix <project-path>` verifies the installed refusal hook, settings helper, and platform wrapper chain, then exercises the helper's process-scoped settings construction, including empty-source isolation and legacy-global environment validation. It does not require `.claude/settings.json`. A missing or invalid link downgrades the result. On native macOS/Linux the matrix reports the strict shell-write policy as configured, but keeps the write boundary at `contained-partial`: this static probe does not execute a behavioral host-sandbox test or resolve administrator-managed exceptions. The read boundary and overall row are also `contained-partial` because shell reads are not capability-scoped and have no equivalent reliable detection record. WSL2 activated launches are refused pending seccomp-layer attestation. On native Windows the activated helper probe is deliberately refused pending both shell-sandbox and native-executable-chain attestation, so the matrix reports `advisory+detection` with that refusal detail rather than presenting a runnable `contained-partial` boundary.

Hosts without a native interception point carry the `advisory+detection` ceiling. opencode is one: it has no filesystem sandbox and no PreToolUse-hook equivalent, and its `edit` permission rules do not cover shell writes (a denied structured write is one shell redirect away from landing anyway), so Cartopian deliberately injects no permission policy there and the matrix reports the detection floor honestly rather than presenting a bypassable rule set as a boundary.

Hermes carries the same ceiling, on stronger evidence: its one-shot mode (the only non-interactive launch the wrapper can use) internally sets `HERMES_YOLO_MODE=1` and `HERMES_ACCEPT_HOOKS=1`, so a wrapper-launched Hermes has no approval layer at all and no wrapper flag can restore one; its write guards (`write_file`/`patch` denylist, `HERMES_WRITE_SAFE_ROOT`) are documented as bypassable via the `terminal` tool by design; and its container backends are host-side configuration Cartopian cannot attest. The wrapper therefore injects no permission policy — a wrapper-set write guard the terminal tool sidesteps would misrepresent containment — and the matrix reports the detection floor.
